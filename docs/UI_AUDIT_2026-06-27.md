## 3. P0 问题详解

### B-DBSEM-001 (P0)

**标题**：`isDbEmpty()` 语义错误，DB 中真实日志/活动被屏蔽

**现象**

- SQLite `logs` 表实际有 **7,437 行**真实日志（来自 [coordinator/route.ts:47](../ui/src/app/api/pipeline/coordinator/route.ts) `createLog()` 写入）
- 但 Logs API 走 mock 分支返回 `mockLogs`（2026-04-28 的死数据）
- Activity Feed 同样，DB `activities` 表有 2 行但 API 返回 `[]`

**根因**

[ui/src/lib/db.ts:1152-1167](../ui/src/lib/db.ts)：

```typescript
export function isDbEmpty(): boolean {
  const outDir = path.join(PARENT_DIR, "output");
  try {
    if (fs.existsSync(outDir)) {
      const hasMd = fs.readdirSync(outDir).some((f) => f.endsWith(".md"));
      if (hasMd) return true;        // ← 看到 output 有 .md 就直接 return true
    }
  } catch { /* ignore */ }
  const db = getDb();
  const count = Number(/* COUNT bookmarks */);
  return count === 0;
}
```

逻辑：「如果 output 里有任何 .md 文件，就走 fs 数据源」。

但 `logs/route.ts` 和 `activity/route.ts` 都用这个判断，结果：
- `if (isDbEmpty()) { return mockLogs }`
- `if (isDbEmpty()) { return { items: [], total: 0 } }`

DB 里的真实日志被完全屏蔽，永远拿到 mock / 空。

**影响**

- 用户看不到真实管线日志（看到的是 4 月份的 mock）
- Activity Feed 永远空，影响 Dashboard 完整性

**修复建议**

两种方案：

**方案 A（推荐）**：把语义拆开
- 把 `isDbEmpty()` 改名为 `prefersFsForBookmarks()`（仅 Bookmarks/Articles 业务用）
- 新增 `hasDbLogs()` / `hasDbActivities()` 独立判断
- `logs/route.ts` 改用 `hasDbLogs()`；`activity/route.ts` 改用 `hasDbActivities()`

**方案 B（小改）**：让 logs / activity API 直接读 DB 不再走 isDbEmpty
- 删除 `if (isDbEmpty()) { mock... }` 分支
- DB 真为空时返回空数组而非 mock

**优先级**：必须修复，影响用户基本可观测性。

### B-DASH-001 (P0)

**标题**：Dashboard 显示「Bookmarks: 642」实际应为 1,584

**现象**

`/api/dashboard/stats` 返回：
```json
{ "totalBookmarks": 642, "totalDrafts": 642, "articlesWritten": 1129, "notionTotalUploaded": 1129 }
```

但 `twitter_data/bookmarks.json` 真实是 **1,584 条**。UI 卡片对用户撒谎。

**根因**

[stats/route.ts:36-45](../ui/src/app/api/dashboard/stats/route.ts)：

```typescript
const stats: DashboardStats = {
  totalDrafts: fsStats.totalDrafts,
  totalBookmarks: fsStats.totalDrafts,   // ← 直接把 drafts 当 bookmarks
  ...
};
```

[fs-data.ts:537-559](../ui/src/lib/fs-data.ts) 的 `countDeepDrafts()` 扫的是 `output/bookmark-deep-*.md`，归档目录的不算，返回 642。所以 totalBookmarks 也是 642。

**为什么这样写**：原设计假定「书签 = 已生成深度报告的书签」，把 bookmarks.json 当成单纯的数据源不直接展示。但用户期望「Bookmarks」卡片反映原始书签总数。

**影响**

- 用户严重低估实际书签量（1,584 - 642 = 942 条书签在 UI 上"看不见"）
- 数据语义混乱，对管理决策有误导

**修复建议**

1. 让 `fs-data.ts` 新增 `countTotalBookmarks()`：读 `twitter_data/bookmarks.json` 数组长度
2. `stats/route.ts` 用真实书签数填 `totalBookmarks`，与 `totalDrafts` 区分
3. UI 卡片标签更清晰：「书签总数 1,584」「已生成深度报告 642」分两个卡片

### B-BOOK-001 (P0)

**标题**：Bookmarks 页面读的是 deep drafts 文件，不是真书签

**现象**

- `/bookmarks` 页只展示 642 条，每条 `id` 形如 `bookmark-deep-2070160491360780798-20260625_190034`
- `bookmarkedAt` 字段实际是文件 mtime，不是 Twitter 上的收藏时间
- `stats.likes/retweets/views` 是从深度报告 frontmatter 的 emoji（❤️ ↻ 🔖 👁 💬）解析的，**不准确**
- 用户无法查看：处于待处理状态的书签（942 条未生成深度报告）、归档书签

**根因**

[fs-data.ts:306-366 listDraftBookmarks](../ui/src/lib/fs-data.ts)：

```typescript
const files = fs.readdirSync(OUTPUT_DIR).filter((f) => f.startsWith("bookmark-deep-") && f.endsWith(".md"));
for (const file of files) {
  // ... 解析每个 deep draft md 文件
  drafts.push({
    id: file.replace(".md", ""),         // ← 文件名当 ID
    bookmarkedAt: meta.PublishedAt || new Date().toISOString(),
    stats: parseStats(meta.Stats || ""),
    ...
  });
}
```

整个 fs-data 没有任何代码读 `twitter_data/bookmarks.json`。Bookmarks 业务在设计上就是「展示有深度报告的那部分书签」，但 UI 标签让用户以为是「全部书签」。

**影响**

- 详情页 URL 又长又丑（`/bookmarks/bookmark-deep-{tid}-{ts}`）
- 真书签 ID（`2070160491360780798`）需要从文件名提取，调用链复杂
- bookmark 统计数据（点赞/收藏数）基于二次解析的 frontmatter emoji，不可靠
- 上游 1,584 条原始数据完全不在 UI 可见范围

**修复建议**

重构 Bookmarks 数据源：

1. fs-data 新增 `listAllBookmarks()`：读 bookmarks.json，每条用真实 tweet `id`、`createdAt`、`tweetBy.userName`、互动数据
2. `/api/bookmarks/route.ts` 优先使用 listAllBookmarks
3. 给每条 bookmark 加 `hasDeepDraft: boolean` / `hasArticle: boolean` / `inNotion: boolean` 三状态标志（join 深度报告/article-final/notion-finished-state）
4. UI 列表加 filter：全部 / 待处理 / 已生成报告 / 已入 Notion

### B-CRON-DEAD (P0)

**标题**：Schedule 的 Cron 设置完全不生效

**现象**

- Settings → Schedule 选 "Every 12 hours" 保存
- `.env` 写入 `CRON_EXPRESSION=0 */12 * * *`
- 但 launchd 仍然每 3 小时跑（plist 硬编码 `StartCalendarInterval`）
- UI 上完全没有提示「这个设置只对内置 timer 有效，launchd 不读」

**根因**

两套调度系统并存且互不相通：

| 系统 | 配置位置 | 实际生效 |
|---|---|---|
| Built-in Timer（Next.js 内置） | `.env.CRON_EXPRESSION` | 需要 dashboard 长开，且默认 disabled |
| macOS launchd | `~/Library/LaunchAgents/com.tizer.bookmark-auto.plist` 的 `StartCalendarInterval` | 始终生效，每 3 小时 |

[settings/route.ts:36](../ui/src/app/api/settings/route.ts)：把 `cronExpression` 存到 `.env`，但 `auto_run.sh` 和 plist 都不读 .env 的 `CRON_EXPRESSION`。

UI [ScheduleSettings.tsx](../ui/src/components/settings/ScheduleSettings.tsx) 同时展示 cron 编辑器和 launchd 管理面板，没有清晰说明两者关系，用户改 cron 以为是改 launchd。

**影响**

- 用户认为修改了调度但实际没生效（误导）
- 「Built-in Timer」概念用户难以理解（什么是「dashboard 开着时」才有效？）
- 修改 launchd 实际频率需要手动编辑 plist + `launchctl unload/load`

**修复建议**

三选一：

**方案 A（最干净）**：删除 cron 编辑器，只保留 launchd
- 把 launchd plist 的 `StartCalendarInterval` 暴露为编辑面板（GET /api/schedule/launchd 读 plist → 前端展示并允许编辑 → PUT 时改写 plist + reload）

**方案 B**：让 cron 真正驱动 launchd
- 用户改 cron 后，API 自动改写 plist 的 `StartCalendarInterval`（cron 转换为 hour/minute 字典数组）+ 自动 reload
- 删除「Built-in Timer」概念

**方案 C（最小改）**：保留现状但加明显提示
- 在 cron 编辑器上加红色横幅：「此设置仅对内置定时器有效，不影响 macOS launchd」
- launchd 面板增加只读的当前 schedule 显示

推荐 A 或 B。当前用户体验完全错误。

### B-SYNC-TERM (P1)

**标题**：Sync 终端不显示子进程实时输出

**现象**：Sync 页 Terminal 永远只显示一行 `sync_bookmarks started: bash sync_bookmarks.sh`

**根因**：[sync/page.tsx:44-53](../ui/src/app/sync/page.tsx) 的 SyncTerminal 只接 `currentOperation.command` 拼接的字符串，没有订阅子进程 stdout 实时流。子进程实际输出写到了 DB `logs` 表（通过 `pipeOutputToLogger`），但 UI 没把这条数据拉过来。

**修复建议**：
1. 新增 SSE 或 polling endpoint `/api/logs/stream?component=coordinator`，每 1s 返回最新 N 条
2. SyncTerminal 订阅这个 stream，渲染滚动日志
3. 区分 stdout / stderr 着色
